# Формы

`Form::of(value)` редактирует модель или entity. Поля берутся из ссылок на поля, подписи из файлов локалей, а проверка из атрибутов `#[rule]`, поэтому браузер и сервер проверяют одни и те же правила.

## Форма

```rust
Form::of(Contact { quantity: 1, ..Contact::default() })
    .row(|r| r.field(Contact::name).field(Contact::email))
    .row(|r| r.field(Contact::quantity).field(Contact::size))
    .submit(t!("docs.live.send"), send_contact)
    .on_success(|_, ui| ui.toast(t!("docs.live.sent")))
```

@live form

Оставьте имя пустым или введите неверный адрес электронной почты и нажмите *Send*: браузер сразу покажет ошибку, а сервер отклонил бы тот же ввод с тем же сообщением.

## Раскладка

| Вызов | Результат |
|---|---|
| `.field(M::f)` | Одно поле на отдельной строке |
| `.row(\|r\| r.field(a).field(b))` | Поля рядом; на узких экранах они выстраиваются друг под другом |
| `.section(title)` | Группа полей после неё с заголовком |
| `.settings()` | Раскладка настроек: подпись и подсказка рядом с каждым полем и панель сохранения, прилипающая к низу после первого изменения |
| `.step(title)` | Шаг мастера; форма показывает по одному шагу |
| `.range(M::from, M::to)` | Две даты как один выбор диапазона |
| `Form::auto(value)` | Все поля в порядке объявления |

Формы не шире 720 px, а карточка или панель, в которой есть только форма, шириной с форму, поэтому половина карточки не пустует. Подписи стоят на 6 px выше полей ввода высотой 36 px; между полями 20 px. Поле в фокусе получает рамку цвета фокуса и мягкое кольцо 3 px, неверное поле получает рамку цвета опасности. Единицы, валюта и `%` рисуются приглушённо внутри поля, а числовые поля ставят кнопки минус и плюс (28 px) внутрь конца поля; клавиши со стрелками по-прежнему меняют значение.

## Сохранение

`.submit(label, action)` называет action, который сохраняет данные. Action должен принимать `Valid<M>` для модели формы; иначе код не компилируется. Runtime отправляет значения, сервер выполняет все правила, затем action.

- Ошибки полей от правил или от `ValidationErrors` в action появляются рядом с полями.
- `Error::Conflict` (устаревший `#[version]`) показывает сообщение о том, что запись изменил кто-то другой.
- `.on_success(|result, ui| ...)` выполняет эффекты после успешного сохранения (см. [Effects и окна](effects.md)).

## Элементы управления

У каждого типа поля есть элемент управления по умолчанию: текстовые поля, числовые поля, деньги с валютой, выбор даты и времени, флажки для `bool` и выпадающие списки для choice. `.control(M::f, Control::...)` выбирает другой, а `.lookup(M::f, action)` ищет записи на сервере. См. [Controls and pickers](controls.md).

## Зависимые lookup

`.depends_on(field, source)` делает варианты lookup `field` зависимыми от другого поля, например города страны. Каждый поиск передаёт значение `source` в `LookupQuery::parent` (`q.parent_id()` читает его как id), а при изменении `source` поле `field` очищается, так что его варианты загружаются заново для нового значения.

```rust
#[action(permission = "geo.read")]
pub async fn find_cities(q: LookupQuery, store: Cities) -> Result<Page<LookupItem>> {
    Ok(q.apply(store.of_country(q.parent_id())))
}

Form::of(address)
    .lookup(Address::country, find_countries)
    .lookup(Address::city, find_cities)
    .depends_on(Address::city, Address::country)
    .submit(t!("save"), save_address)
```

Браузеру эту пару доверить нельзя, поэтому при отправке сервер снова спрашивает action lookup о выбранном городе с отправленной страной, с разрешением этого action, и отклоняет город, которого оно не возвращает, с ошибкой поля. Фильтруйте по родителю и в запросах по id, как это делает `q.apply` после фильтрации. `App::check_page` сообщает о `depends_on`, поле которого не является lookup формы или источник которого не является другим полем формы.

## Формы фильтров

Форма без кнопки отправки может фильтровать экран: `.drives(topic)` делает её поля params экрана. Когда поле меняется (список выбора, диапазон дат, текстовое поле по Enter), его значение попадает в param экрана с тем же именем, адрес поддерживается в актуальном виде, а узлы с `.listens(topic)` обновляются на месте и читают значение из своих params (см. [Темы](effects.md#topics)). Числа и логические значения передаются как есть, пустые поля как `null`; сервер читает params как типизированные params экрана, поэтому неподходящее значение отклоняется.

```rust
#[params]
pub struct SalesParams {
    pub region: Option<Region>,
    pub from: Option<Date>,
    pub to: Option<Date>,
}

#[screen(route = "/sales", permission = "sales.read")]
pub fn sales(p: SalesParams, store: Sales) -> Screen {
    Screen::new(t!("sales.title"))
        .body(
            Form::of(SalesFilter { region: p.region, from: p.from, to: p.to })
                .field(SalesFilter::region)
                .range(SalesFilter::from, SalesFilter::to)
                .drives("sales"),
        )
        .body(Kpi::new(t!("sales.total"), store.total(&p)).listens("sales"))
}
```

Форма с `submit` не может управлять темой; вместо этого обновляйте после сохранения через `ui.refresh(topic)` в `on_success`.

## Поля только для чтения

Поля `#[readonly]` показываются в формах, но не редактируются, например остаток на складе, который меняют только движения.

## Загрузка файлов

Поля `File`, `Option<File>` и `Vec<File>` хранят файлы, которыми управляет `FileStore`. Объявите правила один раз как `const`, зарегистрируйте хранилище в Feature с разрешением и используйте те же правила в форме:

```rust
pub const ATTACHMENTS: FileRules = FileRules::new("attachments")
    .max_bytes(5 * 1024 * 1024)
    .max_files(5)
    .accept(&[FileType::Pdf, FileType::Png, FileType::Jpeg]);

Feature::new("support")
    .files(ATTACHMENTS, "support.ticket.files", DiskStore::new("data/attachments"))
    .scan_files(MyVirusScanner)

Form::of(ticket).field(Ticket::title).file(Ticket::attachments, ATTACHMENTS)
```

Одно имя разрешения даёт одним и тем же пользователям и загрузку, и скачивание. Чтобы читатели могли открывать файлы, которые им нельзя добавлять, разделите его: `.files(ATTACHMENTS, FileAccess::read("support.ticket.read").write("support.ticket.files"), store)`.

Элемент управления это встроенное поле выбора файла внутри зоны перетаскивания. Каждый файл загружается отдельно с индикатором хода, его можно отменить во время загрузки, повторить после сбоя и удалить после завершения. Для изображений показывается превью, созданное из object URL выбранного файла. Ход загрузки и результаты объявляются в вежливой live-области (polite live region). В showcase есть рабочий пример по адресу `/uploads`; на этом сайте документации нет вошедшего пользователя, поэтому живой загрузки здесь нет.

Перетащенная папка добавляет файлы из неё и её подпапок; папка читается страницами не более чем по 100 записей, пока не закончится. Файлы типа, который поле не принимает, пропускаются, а их число объявляется в живой области. Файлы, вставленные, пока поле в фокусе, тоже загружаются. Файл, расширения или типа которого нет в `accept`, отклоняется в браузере до отправки первого байта, а сервер ещё раз проверяет содержимое. Одновременно загружаются не более трёх файлов поля; остальные ждут в очереди с индикатором занятости.

| Клавиша | Что делает |
|---|---|
| Tab | Переходит к полю выбора файла, затем к ссылке скачивания каждого файла и к его кнопке Cancel, Retry или Remove |
| Enter или Space на поле выбора файла | Открывает системное окно выбора файла (путь с клавиатуры для перетаскивания) |
| Ctrl+V или Cmd+V в поле файла | Загружает файлы из буфера обмена, например снимок экрана |
| Enter или Space на Cancel, Retry, Remove | Выполняет действие; после Cancel фокус переходит на Retry, после Remove на следующий файл или обратно на поле |

Что сервер делает для `POST /_zeyn/files/{store}`:

1. проверяет заголовок CSRF, разрешение хранилища и guard Feature и запускает перехватчики (`CallKind::Upload`, аудит с идентификатором нового файла); загрузки учитываются в лимите записи;
2. отклоняет объявленный `Content-Length` сверх лимита (`413`), затем читает первые 4 КиБ и определяет тип по содержимому; расширение должно принадлежать тому же типу, а тип должен входить в `accept`, иначе `415`. HTML, SVG, XML и скрипты не принимаются никогда. Тип содержимого, заявленный браузером, игнорируется;
3. передаёт остальное в хранилище потоком порциями не более 64 КиБ через канал на четыре элемента, подсчитывая байты; превышение лимита, обрыв соединения или 30 секунд без данных останавливают загрузку, и хранилище удаляет то, что записало;
4. запускает `FileScanner` Feature; отклонённый файл или сканер, который дал сбой, приводят к удалению файла и ответу `422`;
5. отвечает `201` с `{id, name, size, type}`. Идентификатор это 128 случайных бит, созданных сервером; из имён удаляются пути и управляющие символы.

С функцией `image` метод `FileRules::clean_images()` добавляет шаг после того, как хранилище получило файл: загрузки PNG, JPEG и WebP декодируются и заново кодируются в том же формате, поэтому EXIF (с GPS), XMP, профили ICC, текстовые блоки и байты, спрятанные после данных изображения, не остаются на сервере. Ориентация EXIF сначала применяется к пикселям; JPEG записывается с качеством 90, PNG и WebP без потерь. Декодирование останавливается на `MAX_IMAGE_SIDE` (12 000) пикселей по стороне и `MAX_IMAGE_MEMORY` (256 МиБ); изображение, которое не декодируется, удаляется, и ответ `422`. Оба предела проверяются по размеру из заголовка изображения до декодирования любого пикселя, поэтому маленький файл, заявляющий огромное изображение, отклоняется без выделения этой памяти, а от анимированного изображения остаётся только первый кадр. Очищенный файл заменяет исходный под новым id, а затем сканер проверяет очищенный файл. Без функции метода нет, так что хранилище не может считать себя очищенным, когда это не так.

Скачивания (`GET /_zeyn/files/{store}/{id}`) проверяют форму идентификатора, разрешение, guard и арендатора (tenant) и проходят через выдачу медиа (см. `docs/media.md`): диапазоны, entity tag и `nosniff`. Встроенно (inline) отдаются только растровые изображения, аудио и видео; всё остальное отправляется как `application/octet-stream` с `Content-Disposition: attachment`, с именем в кавычках в ASCII плюс именем в UTF-8, под `Content-Security-Policy: sandbox`.

`DiskStore` хранит `{id}.bin` и `{id}.json` в одной папке и сначала записывает загрузки в `{id}.part`. `MemoryStore` держит файлы в памяти с ограничением по байтам, для тестов и демонстраций. Значение формы лишь называет файлы: action сохранения, которому нужно быть уверенным, что файл существует, вызывает `store.meta(id)`, как это делает showcase.

`FileRules::quota(bytes, window)` ограничивает, сколько один пользователь загружает в хранилище за окно, и считается через rate store приложения; загрузка, которая превышает лимит, всё равно сохраняется, а следующая получает `429`. `DiskStore` удаляет файлы `.part` старше часа (загрузки, прерванные сбоем) не чаще раза в час. `ZipGuard` проверяет загрузки на основе ZIP (ZIP, Word, Excel, PowerPoint): он отклоняет архивы, центральный каталог которых объявляет больше 10 000 записей, больше 1 GiB в сумме или больше чем в 200 раз больше размера файла, а также архивы ZIP64; код, распаковывающий принятый архив, всё равно должен останавливаться на этих пределах.

Бюджет: загрузка 256 МиБ увеличивает кучу сервера примерно на 0,4 МиБ (`tests/files_memory.rs`); элемент управления отрисовывает 10 узлов DOM плюс 5 на каждый файл; `files.js` добавляет 21 КБ в исходном виде и 7 КБ в gzip, `files.css` 3 КБ в исходном виде и 1 КБ в gzip.

### Возобновляемые загрузки

С функцией Cargo `resumable` поле загрузки и `FileDrop` отправляют файлы по подмножеству протокола tus 1.0, поэтому загрузка, потерявшая сеть, продолжается с места остановки, а не начинается заново. Сам элемент управления менять не нужно:

```toml
zeyn = { version = "0.0", features = ["resumable"] }
```

```rust
App::new("Support").resumable_uploads(
    ResumableUploads::new("data/uploads")
        .expires(Duration::from_secs(6 * 3600))
        .max_per_user(3)
        .max_open(500),
)
```

Без `resumable_uploads` незавершённые загрузки попадают во временную папку системы, хранятся 24 часа после последних байтов, и открытыми могут быть не более 5 на пользователя и 1000 всего.

| Запрос | Ответ |
|---|---|
| `POST /_zeyn/uploads/{store}` с `Upload-Length` и `Upload-Metadata: filename <base64>` | `201` с `Location`, `Upload-Offset: 0` и `Upload-Expires`; `413` сверх лимита хранилища, `422` для пустого файла, `429` сверх квоты или лимитов открытых загрузок |
| `HEAD` по адресу | `200` с `Upload-Offset` и `Upload-Length` |
| `PATCH` с `Content-Type: application/offset+octet-stream` и `Upload-Offset` | `204` с новым `Upload-Offset`; `409`, если смещение не совпадает с серверным, `423`, пока выполняется другой `PATCH` той же загрузки, `413` при байтах сверх объявленных |
| `PATCH`, который приносит последний байт | `200` с `{id, name, size, type}`, как обычная загрузка |
| `DELETE` по адресу | `204`; загрузка и её байты удаляются |

Каждому запросу нужны `Tus-Resumable: 1.0.0` (иначе `412`), право записи в хранилище и guard'ы функции; `POST`, `PATCH` и `DELETE` также требуют заголовок CSRF. Загрузку находит только создавший её пользователь в своём тенанте; все остальные получают `404`. Создание загрузки учитывается в лимите записи, как обычная загрузка; её `PATCH` не учитываются, так как не могут нести больше объявленной длины. Браузер отправляет файл запросами `PATCH` по 1 MiB, это лимит тела по умолчанию у распространённых обратных прокси, поэтому разрыв соединения стоит не больше этого объёма повторно.

Байты записываются в `{id}.part` в папке загрузок по мере поступления, поэтому байты, дошедшие до сервера до разрыва соединения, сохраняются, и `HEAD` их сообщает. Когда приходит последний байт, файл проходит те же шаги, что и `POST /_zeyn/files/{store}`: тип по содержимому, лимит размера, квота, хранилище, сканер и перехватчики (`CallKind::Upload`). Затем файл части удаляется, также когда проверка отклоняет файл. Загрузка без новых байтов в течение срока хранения удаляется при следующем обращении к ней или при создании следующей загрузки; файлы частей, оставшиеся после перезапуска, вычищаются раз за срок хранения.

В браузере неудачный запрос (потеря сети, `409`, `423`, `429` или ошибка сервера) повторяется через 1, 2, 4, 8, а затем каждые 15 секунд, после того как браузер снова в сети, до 12 раз подряд; каждая попытка сначала запрашивает смещение и отправляет только остаток. Отмена останавливает запрос и удаляет загрузку на сервере. Повтор после окончательной ошибки продолжает ту же загрузку, пока она есть на сервере.

Отличия от tus 1.0: только расширения creation, expiration и termination; нет обнаружения через `OPTIONS`, контрольных сумм, отложенной длины и конкатенации; последний `PATCH` отвечает `200` с сохранённым файлом вместо `204`, чтобы поле получило id файла без ещё одного запроса. Открытые загрузки известны только процессу, который их создал, поэтому за балансировщиком с несколькими экземплярами пути `/_zeyn/uploads/` требуют липких сессий (sticky sessions).

## File drop

`FileDrop::new(label, rules)` это тот же элемент загрузки сам по себе, вне формы, для экранов, где файлы и есть вся задача, например входящие документы. Как и поле формы, он принимает папки, вставленные файлы и список accept и загружает в хранилище `rules`, которое `Feature::files` регистрирует вместе с разрешением. `.single()` принимает один файл за раз. `.on_upload(action)` запускает действие для каждого сохранённого `File`; сервер сначала проверяет, что id имеет форму, которую он создаёт, ещё раз очищает имя и оставляет только тип содержимого из правил, так что действие не получает ничего придуманного браузером. Если действие отказывает, элемент показывает причину. Выбор файлов внутри зоны служит путём для клавиатуры и одного указателя.

```rust
#[action(permission = "support.ticket.files")]
pub async fn attach(file: File, tickets: Tickets) -> Result<()> {
    tickets.attach(file).await
}

FileDrop::new(t!("ticket.attachments"), ATTACHMENTS).on_upload(attach)
```
