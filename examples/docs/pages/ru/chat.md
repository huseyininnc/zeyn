# Чат

Компоненты для переписки: сообщения разговора, поле, в котором пишет пользователь, и пометка о том, что кто-то печатает. Каждый из них отрисовывается на сервере и загружает свою таблицу стилей и скрипт только на тех страницах, где он используется.

## MessageThread

`MessageThread` показывает сообщения одного разговора в виде пузырей чата: собственные сообщения пользователя на конечной стороне, остальные на начальной (зеркально в языках с письмом справа налево), идущие подряд сообщения одного отправителя в пределах пяти минут сгруппированы под одним именем, заголовок для каждого дня в часовом поясе пользователя, время каждого сообщения и, у собственных сообщений, состояние доставки.

```rust
#[action(permission = "chat.read")]
pub async fn conversation_messages(q: ThreadQuery, store: Chats, ctx: Ctx) -> Result<Page<Msg>> {
    store.check_member(&q.conversation, &ctx)?;
    Ok(q.query.apply(store.messages(&q.conversation)))
}

MessageThread::of(conversation_messages)
    .conversation(params.id.to_string())
    .author(Msg::author)
    .name(Msg::author_name)
    .text(Msg::body)
    .when(Msg::sent_at)
    .status(Msg::status)
    .attachments(Msg::files, CHAT_FILES)
    .live()
```

Action истории принимает `ThreadQuery`: разговор, который сервер берёт из компонента (браузер его никогда не отправляет), и `DataQuery`, отсортированный от новых к старым. Проверьте в action, что пользователь участвует в разговоре. `.author` это id пользователя-отправителя; его сравнивают с вошедшим пользователем, чтобы отличить собственные сообщения от чужих. `.name` это отображаемое имя. Модели нужен `#[key]`, поэтому сообщение, загруженное дважды, показывается один раз.

Первые 50 сообщений (`THREAD_PAGE`) отрисовываются вместе с экраном. Прокрутка вверх загружает следующую, более старую страницу через `POST /_zeyn/grid`, каждый раз с проверкой доступа к экрану и разрешения action, и сообщение, на которое смотрит читатель, остаётся на месте. На странице остаётся не больше 200 сообщений: при дальнейшей прокрутке дальний конец отбрасывается и загружается снова, когда читатель возвращается, поэтому разговор из тысяч сообщений занимает столько же памяти, сколько короткий. Прокрутка 5 000 сообщений идёт с частотой кадров дисплея, при этом на странице около 2 000 элементов.

У `Delivery` есть состояния `Sending`, `Sent`, `Delivered`, `Read` (отметка о прочтении) и `Failed`; каждое показывается значком и текстом для экранных дикторов. `.attachments(field, rules)` показывает файлы сообщения (поле `Vec<File>` и правила хранилища, зарегистрированного через `Feature::files`): изображения в блоке фиксированного размера, который лениво загружается поверх заглушки, остальные файлы в виде ссылок для скачивания, проходящих через разрешение на чтение хранилища.

Новые сообщения запрашиваются, когда называется один из topic ветки, `"chat"`, если `.topic(..)` не задаёт другой: после отправки из `Composer`, после того как action завершается `ui.refresh("chat")`, или, с `.live()` и feature `realtime`, когда где-либо выполняется `hub.notify(&ctx, "chat")`. Сообщения других людей объявляются в вежливой (polite) живой области.

### Ответы ИИ

```rust
#[action(permission = "chat.ai")]
pub async fn ask_model(r: ReplyRequest, store: Chats) -> Result<Reply> {
    let id = store.reserve_id();
    let (tx, reply) = Reply::channel(id.to_string());
    tokio::spawn(async move {
        let mut text = String::new();
        for piece in my_model_stream(&r.text).await {
            text.push_str(&piece);
            if !tx.send(piece).await {
                break;
            }
        }
        store.save_ai_answer(id, &r.conversation, text);
    });
    Ok(reply)
}

MessageThread::of(conversation_messages)
    .conversation(id)
    .ai(Msg::from_ai)
    .reply(ask_model)
```

С `.reply(action)` сообщение, отправленное из `Composer` того же разговора, запускает ответ ИИ: браузер отправляет текст на `POST /_zeyn/stream` (CSRF, лимит записи, доступ к экрану, разрешение action и интерсепторы), и ответ приходит потоком в виде строк JSON в формате встроенного ассистента. Фрагменты проходят через ограниченный канал (`REPLY_BUFFER`); сервер останавливается после `MAX_REPLY_CHARS` (32 000) символов или `REPLY_SECONDS` (120) секунд, а кнопка остановки завершает ответ раньше. `ReplySender::send` возвращает `false`, когда читатель ушёл; это сигнал генератору остановиться.

Ответ показывается как небольшое подмножество Markdown, построенное только из текстовых узлов, поэтому ничто из написанного моделью никогда не разбирается как HTML. Предыдущие сообщения никогда не перерисовываются, перерисовывается только абзац, который сейчас пишется: ответ из 2 000 фрагментов в конце стоит на кадр столько же, сколько в начале, и ничто над ним не сдвигается. Живая область зачитывает ответ один раз, когда он закончен, и никогда по фрагментам. Сообщения, помеченные `.ai(field)`, тоже загружаются из истории как безопасный Markdown (с feature `markdown`; без неё как простой текст).

Ключ ответа (`Reply::channel(key)`) это ключ, который будет у сохранённого сообщения, поэтому история показывает сохранённый ответ на его месте, а не вторую копию.

## Composer

`Composer` это поле, в котором пользователь пишет сообщения: текстовая область, которая растёт вместе с текстом до максимальной высоты, кнопка отправки и, по запросу, вложения, упоминания и сохраняемый черновик.

```rust
#[action(permission = "chat.write")]
pub async fn send_message(m: ChatSend, store: Chats, hub: Hub, ctx: Ctx) -> Result<()> {
    store.check_member(&m.conversation, &ctx)?;
    store.add(&m.conversation, &ctx, m.text, m.attachments, m.mentions)?;
    hub.notify(&ctx, "chat");
    Ok(())
}

pub const CHAT_DRAFTS: ClientPref<Draft> =
    ClientPref::draft("chat-draft", Duration::from_secs(7 * 86_400), Purpose::Preference);

Composer::of(send_message)
    .conversation(params.id.to_string())
    .attachments(CHAT_FILES)
    .mentions(search_people)
    .remember(CHAT_DRAFTS)
```

Action отправки принимает `ChatSend`: разговор, который сервер берёт из компонента, обрезанный текст, вложенные файлы и id упомянутых людей. Отправка идёт через `POST /_zeyn/data` с токеном CSRF, учитывается в лимите записи и требует разрешения action; composer, через который пользователь не может отправлять, не попадает на страницу. Сервер отклоняет пустое сообщение, сообщение длиннее `.max_chars(n)` (4 000, если не задано), больше файлов, чем позволяют правила хранилища, id файлов неверного вида и больше 20 упоминаний. Остальное тоже считайте недоверенным: проверьте, что пользователь участвует в разговоре и может упоминать этих людей.

`SendKey::Enter`, значение по умолчанию, отправляет по Enter и начинает новую строку по Shift+Enter; `.send_key(SendKey::CtrlEnter)` отправляет по Ctrl+Enter (Cmd+Enter на Mac) и оставляет Enter для новых строк. Кнопка отправки отключена, пока сообщение пустое или слишком длинное, а рядом с лимитом появляется счётчик. После отправки composer называет свои topic (`"chat"`, если `.topic(..)` не задаёт другой), поэтому `MessageThread` того же разговора сразу показывает сообщение и передаёт потоком ответ ИИ, если у него есть `.reply(..)`.

`.attachments(rules)` добавляет поле загрузки хранилища, зарегистрированного через `Feature::files`: файлы загружаются по одному на `POST /_zeyn/files/{store}` с индикатором прогресса, с разрешением на запись и проверками типа хранилища, а их id уходят вместе с сообщением.

`.mentions(action)` ищет людей после `@` с помощью action поиска (на входе `LookupQuery`, на выходе страница `LookupItem`). Поиск начинается через 200 ms после последнего нажатия клавиши, новый поиск отменяет старый, а сервер запрашивает не больше `MAX_MENTIONS` (8) человек и возвращает не больше этого. Список это listbox, управляемый из текстовой области: стрелки перемещают, Enter или Tab выбирают, Escape закрывает.

`.remember(key)` хранит неотправленный текст каждого разговора в хранилище клиентских настроек под ключом `Draft`, зарегистрированным через `App::client_prefs`, пока текст не отправлен. Черновик содержит не больше `MAX_DRAFT_CHARS` (4 000) символов, хранится не больше `MAX_DRAFTS` (20) разговоров, и первым удаляется самый старый. Id разговора хранится только в виде хеша. С `Purpose::Preference` черновики остаются на время сеанса, пока пользователь не даст согласие на большее.

## TypingIndicator

`TypingIndicator` показывает, кто ещё печатает в разговоре: "Ada печатает", "Ada и Grace печатают", "3 человека печатают", в вежливой (polite) живой области.

```rust
let realtime = Realtime::new().topic("chat", "chat.read");

TypingIndicator::new("chat")
    .conversation(params.id.to_string())
    .person("ada", "Ada Lovelace")
    .person("grace", "Grace Hopper")
```

Он работает через канал реального времени (feature `realtime`, см. `realtime.md`) на topic, объявленном через `Realtime::topic`. Пока пользователь печатает в `Composer` того же разговора, браузер отправляет по живому сокету страницы небольшой сигнал не чаще раза в 3 секунды; сервер отбрасывает более частые сигналы для каждого пользователя и передаёт сигнал остальным подписчикам topic в тенанте, никогда обратно тому же пользователю. Сигнал содержит id разговора и ключ пользователя, который может создать только этот сервер, и никогда не содержит id пользователя или какой-либо текст. Имя показывается 6 секунд после последнего сигнала; люди, не заданные через `.person(user, name)`, отображаются как "кто-то".

Без feature `realtime` или если у приложения нет канала реального времени индикатор ничего не отрисовывает, его скрипт не загружается и ничего не отправляется. Сигналы доходят до всех подписчиков topic в тенанте, поэтому id разговора им виден: используйте непрозрачные id или отдельный topic для каждой аудитории.
