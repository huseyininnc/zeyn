# Таблица данных (Data Grid)

Статус: реализовано в `zeyn::DataGrid`, в endpoint-ах таблицы в `zeyn::server` и в `assets/zeyn/*.js` (отдаются как `/_zeyn/zeyn.js`).

Таблица рендерится на сервере. Её строки приходят из action, который принимает `DataQuery` и
возвращает `Page<E>`. Браузерный runtime запрашивает страницы, отправляет действия пользователя
(сортировка, фильтры, раскладка, правки, действия) и подставляет полученный HTML на место. Каждый
вызов проверяет права на сервере, и ничему, что присылает клиент, не доверяется.

```rust
DataGrid::of(search_products)
    .mode(DataMode::Server)
    .paging(Paging::pages(25))
    .column(Product::code).width(120).pin_start().filter()
        .link(|p| Window::open(product_editor, ProductParams { id: Some(p.id) }))
    .column(Product::name).flex(1).filter().editable()
    .column(Product::unit).filter().editable().badge(|u| match u {
        Unit::Kg => Tone::Info,
        _ => Tone::Neutral,
    })
    .column(Product::price).filter().editable().avg().max()
    .column(Product::stock).filter().sum().progress(120)
    .column(Product::active).filter().check_icon().editable()
    .edit_with(save_product)
    .row_action(t!("stock.restock"), restock_product, |p| p.id)
    .bulk_action(t!("stock.deactivate"), deactivate_products, Product::id)
    .row_menu(|p| ContextMenu::new()
        .item(t!("stock.edit"), Window::open(product_editor, ProductParams { id: Some(p.id) }))
        .action(t!("stock.restock"), restock_product, p.id))
    .exportable()
```

## Колонки, известные во время выполнения

`DataGrid::dynamic(action)` показывает результат, колонки которого известны только после выполнения запроса, например предпросмотр SQL или обозреватель источника данных. Action принимает `DataQuery` и возвращает `DynamicPage`: колонки (`DynamicColumn { name, label, kind }`) и одну страницу строк, каждая из которых JSON массив в порядке колонок или JSON объект по именам колонок.

```rust
#[action(permission = "reports.preview")]
pub async fn preview(q: DataQuery, db: Reports) -> Result<DynamicPage> {
    let span = q.span();
    db.run_preview(span.offset, span.limit).await
}

DataGrid::dynamic(preview).paging(Paging::virtual_scroll())
```

Grid строит свои колонки по каждой странице и выводит строки собственным кодом типизированного grid, поэтому пагинация, виртуальная прокрутка, виртуализация колонок, работа с клавиатуры, копирование, изменение ширины, перемещение и скрытие колонок работают так же. `DynamicKind` задаёт, как колонка читает и показывает значения: `Text`, `Integer` (с группировкой разрядов по локали пользователя), `Decimal`, `Bool` (да и нет на языке пользователя), `Date`, `Time`, `DateTime` (в часовом поясе пользователя) и `LocalDateTime`. Значение, которое не читается как его тип, показывается как текст. Каждая колонка начинается с ширины по своему типу (180 px для текста, 130 для чисел, 120 для дат), поэтому широкий результат прокручивается вбок.

Всё, что возвращает action, считается пользовательскими данными. Имена колонок, подписи и ячейки экранируются, как любые другие значения. Сервер оставляет не больше `MAX_DYNAMIC_COLUMNS` (200) колонок и столько строк, сколько составляет размер страницы запроса (`DataQuery::limit`, не больше 500), и обрезает имена и подписи до `MAX_COLUMN_NAME` (200), а текстовые ячейки до `MAX_CELL_TEXT` (1 000) символов. Ключи сортировки, фильтры, итоги и группы удаляются из запроса до запуска action, а в заголовках нет кнопок сортировки, так что action никогда не получает имя колонки от клиента. Доступ определяется action, как у любого grid.

Пустые имена становятся `col_<номер>`, повторяющиеся получают `_2`, `_3`; объектные строки по-прежнему читаются по собственным именам action. Страница хранит не больше `MAX_PAGE_CELLS` (50 000) ячеек и `MAX_PAGE_TEXT` (8 МБ) текста ячеек. Каждая текстовая ячейка получает равную долю бюджета текста, поэтому широкая страница показывает более короткий текст; строки сверх бюджета ячеек приходят со следующей страницей, на которую указывает `next`. Вложенные значения JSON записываются только до своей доли. Ответ из 500 строк по 200 колонок по 1 000 эмодзи (403 МБ в action) не занял памяти сверх собственного ответа action и отправил 4,6 МБ.

`DynamicColumn::masked(MaskStyle::LastFour)` маскирует колонку сразу при чтении страницы, так что её исходные значения никогда не попадают в HTML, журналы или ИИ-агентам, и никто не может их раскрыть. `DynamicGrid::sensitive(model, key)` записывает в аудит каждую показанную строку как чтение `model` с ключом из колонки `key`, как строки `sensitive` сущности. Без них action сам решает, что может показывать результат.

Когда колонки меняются, браузер отбрасывает строки, сохранённые для старых колонок. Сохранённое представление используется только для тех колонок, для которых оно создано.

Заголовок несёт отпечаток колонок (`data-zeyn-shape`). Браузер отправляет его с каждым запросом страницы, а сервер присылает новый заголовок, только когда колонки изменились, например после того как `.listens(topic)` перезагрузил grid с новым запросом. Строки только для чтения: у динамического grid нет редактирования, действий над строками, выбора, деталей, группировки и экспорта.

## Итоги по столбцам

`sum()` и `avg()` работают с целыми числами и деньгами, `min()` и `max()` также с датами, временем и
моментами, `count()` с любым столбцом. Применение к другому типу не компилируется. Итоги охватывают
все строки, подходящие под фильтры, а не только страницу.

`DataQuery::apply` вычисляет их для данных в памяти. Слой данных, который выполняет постраничную
выборку в SQL, читает `query.aggregates` и добавляет `Page::with_total(field, op, value)` из одного
агрегатного запроса. Таблица оставляет только те итоги, которые объявлены её столбцами, поэтому
клиент не может запросить другие. Итоги форматируются на сервере на языке пользователя. Средние
значения целых чисел имеют два десятичных знака (`Value::Decimal`), а средние значения денег
округляются от нуля (half away from zero) до наименьшей единицы.

## Фильтры и сортировка

`filter()` добавляет фильтр в строку фильтров, а поле ввода выбирается по типу столбца:

| Столбец | Фильтр | Запрос |
|---|---|---|
| Текст | содержит, начинается с, равно | `contains`, `starts_with`, `equals` |
| Целое число, деньги | от, до | `from`, `to` в виде `1234.56` |
| Дата | от, до | `from`, `to` в виде `2026-03-31` |
| Момент (`DateTime`) | от, до (даты) | целый день в часовом поясе пользователя |
| Время | от, до | `14:30` |
| Выбор (Choice) | любой из вариантов | `any_of` |
| Да/нет | все, да, нет | `is` |

Значения передаются в фиксированной машинной форме, независимо от языка пользователя. Старая форма
`{ "field", "contains" }` по-прежнему работает. Сервер отбрасывает фильтры по столбцам без
`filter()` и сортировку по столбцам, которых нет в таблице, а также ограничивает число фильтров (32),
длину текста фильтра (200 символов), число вариантов выбора (100) и число ключей сортировки (4).
Значение, которое не удаётся прочитать, игнорируется. Часовой пояс для фильтров по датам берётся из
настроек пользователя на сервере.

`filter_builder()` добавляет над таблицей кнопку «Фильтр» с числом активных условий, которая
открывает конструктор фильтра: диалог со строкой на каждое условие, где каждая строка это столбец с
`filter()` и поля этого столбца из строки фильтров. «Добавить условие», «Очистить всё» и «Применить»
меняют список; Escape или «Отмена» оставляют его прежним, и фокус возвращается на кнопку. Условия
действуют вместе, а более позднее условие на тот же столбец заменяет раннее. При применении они
записываются в фильтры таблицы, поэтому строка фильтров, сохранённые представления, экспорт и событие
`zeyn:filter` от ИИ агента используют один список, который сервер очищает, как описано выше.

Shift+щелчок по заголовку добавляет этот столбец в ключи сортировки. Число в заголовке показывает
порядок.

## Столбцы: закрепление, размер, скрытие, перемещение

`pin_start()` и `pin_end()` удерживают столбец у одного края при горизонтальной прокрутке таблицы (не
более трёх с каждой стороны). `hidden()` убирает столбец, пока пользователь его не покажет. У каждого
заголовка есть меню столбца (кнопка, щелчок правой кнопкой, Shift+F10 или клавиша контекстного меню):
сортировка, закрепление, перемещение влево и вправо, скрытие, фильтр, выбор столбцов и сброс. Край
заголовка меняет ширину столбца перетаскиванием или стрелками (Shift для больших шагов).
Перетаскивание заголовка на другой заголовок той же закреплённой группы перемещает столбец, а
короткое нажатие по-прежнему сортирует. Всё это работает и в режиме справа налево. Двойной щелчок по краю заголовка, Enter на нём или «Ширина по содержимому» в меню столбца подгоняет столбец под заголовок и строки на странице; «Подогнать все столбцы» делает это для каждого показанного столбца. Ширины сохраняются в представлении.

## Поиск

`search()` показывает поле поиска над таблицей. Введённый текст после короткой паузы попадает в
действие таблицы как `DataQuery::q` вместе с каждой страницей, блоком, веткой, массовым действием
над всеми подходящими строками и экспортом; новый поиск отменяет предыдущий запрос.
`DataQuery::apply` и слои данных SQL сравнивают его с текстовыми полями без учёта регистра и
диакритики и никогда не ищут по маскированным полям. Таблица без `search()` отбрасывает любой `q`,
присланный клиентом. Результат объявляется в живой области таблицы, а если поиск ничего не нашёл,
показывается `empty_filtered`. Текст поиска не входит в сохранённое представление. ИИ агенты
находят `q` в схеме инструмента таблицы.

## Заголовки групп

`band(label, |b| ...)` собирает столбцы, добавленные замыканием, под одной ячейкой заголовка в
строке над заголовками столбцов:

```rust
DataGrid::of(search_products)
    .search()
    .column(Product::code).pin_start()
    .band(t!("stock.price_and_stock"), |b| b
        .column(Product::price).avg()
        .column(Product::stock).sum())
    .column(Product::active)
```

Группа это `th` с `scope="colgroup"` и `colspan` на её показанные столбцы; ячейки над столбцами
вне групп остаются пустыми. Строка групп следует раскладке пользователя: скрытые столбцы выходят из
группы, группа показывает одну ячейку на каждую серию своих столбцов, которые стоят рядом на одной
закреплённой стороне (перенос столбца в сторону делит её), закреплённые серии остаются со своими
столбцами, а виртуализация столбцов сохраняет строку групп целой. Экспорт и копирование группы не
включают.

## Сохранённые представления

Раскладка пользователя (показанные столбцы по порядку, ширины, закрепления), сортировка и фильтры
образуют `DataGridView`. С `App::datagrid_views(store)` он сохраняется на сервере для каждого
пользователя, арендатора (tenant), экрана и таблицы, а страница возвращается уже в нём, с первой
страницей, отсортированной и отфильтрованной. Реализуйте `DataGridViewStore` для базы данных;
`MemoryViewStore` предназначен для разработки и тестов. Без хранилища браузер держит представление в
`localStorage`. Сервер очищает каждое получаемое представление по собственным столбцам и лимитам
таблицы.

## Ячейки

| Метод | Столбцы | Показывает |
|---|---|---|
| `badge(\|v\| Tone)` | enum с `#[choice]` | цветной бейдж для каждого варианта |
| `progress(max)` | числа, деньги | полосу и число |
| `link(\|row\| Effect)` | любые | значение как ссылку, запускающую effect |
| `check_icon()` | `bool` | галочку или прочерк, с текстом для экранных дикторов |
| `relative_time()` | `DateTime` | «3 минуты назад», точное время во всплывающей подсказке |
| `cell(renderer)` | любые | ваш собственный HTML (`CellRenderer<T>`) |

`CellRenderer` обязан экранировать пользовательские данные. Экспорт и копирование используют простое
значение.

## Действия строк, меню и массовые действия

`row_action(label, action, |row| input)` добавляет кнопку в каждую строку. `row_menu(|row|
ContextMenu)` добавляет контекстное меню. `Screen::context_menu(...)` добавляет его в пустое место
экрана. Пункты, запускающие action, показываются только пользователям с правом на этот action.

Когда пункт строки запускается, клиент отправляет только ключ строки и пункт. Сервер заново
загружает строку через action таблицы, строит пункт из этой строки, проверяет право на action,
запускает перехватчики (interceptors), а затем сам action. Пункт, которого для строки больше нет
(например, ставший недоступным), отклоняется. Входные данные никогда не приходят от клиента.

`bulk_action(label, action, Model::key)` добавляет кнопку в панель выбора. Action принимает `Vec<K>`,
где K это тип поля ключа; всё остальное не компилируется. Выбор «всех подходящих строк» позволяет
серверу самому собрать ключи с фильтрами пользователя, до 10 000. Ключи, выбранные по одному,
приходят от клиента, поэтому action должен проверять каждую запись так же, как action API.

Во всех остальных местах браузер сохраняет своё контекстное меню. `App::browser_context_menu(false)`
отключает его везде, кроме текстовых полей и редактируемого текста. Это ничего не защищает:
пользователи по-прежнему могут читать исходный код страницы, открывать инструменты разработчика или
отключать скрипты. Кроме того, пропадают проверка орфографии, копирование ссылки, перевод и
вспомогательные технологии. Оставьте значение по умолчанию.

## Редактирование на месте

`edit_with(save)` с action, принимающим `Valid<E>` (то же правило, что и у форм), и `editable()` для
столбцов. Ключи, поля только для чтения и версии строк никогда не становятся редактируемыми. F2 или
двойной щелчок по редактируемой ячейке начинает редактирование строки; Enter сохраняет, Escape
отменяет, Ctrl+Z или кнопка в уведомлении отменяет последнее сохранение.

Сервер заново загружает строку по ключу и применяет только редактируемые столбцы и версию строки
через `Form::read`, так что значения читаются и проверяются так же, как в форме. Значение для любого
другого столбца отклоняется с `403`. Устаревшая версия возвращается как `409`, а ошибки валидации
возвращаются как `422` и показываются в своих ячейках.

## Добавление, удаление и пакетное редактирование строк

```rust
DataGrid::of(search_products)
    .column(Product::name).editable()
    .column(Product::price).editable()
    .edit_with(save_product)
    .add_with(create_product)
    .delete_with(delete_products, Product::id)
    .batch_edit()
```

`add_with(create)` показывает над таблицей кнопку «Добавить строку». Она открывает сверху пустую
строку с полем ввода для каждого столбца с `editable()`; Enter сохраняет её, Escape отменяет. Сервер
начинает со значения модели по умолчанию, читает только редактируемые столбцы так же, как форма
(любое другое поле отклоняется с `403`, неверные значения возвращаются с `422` и показываются в
своих ячейках), проверяет право на `create` и выполняет его; затем таблица перезагружается.
Виртуальные таблицы строки не добавляют.
Полям, которые модель не может оставить со значением по умолчанию, например обязательной
дате, нужен редактируемый столбец.

`delete_with(action, Model::key)` добавляет в панель выбора красную кнопку «Удалить», которая
спрашивает перед выполнением, а клавиша Delete на строке удаляет выбранные строки или, если выбора
нет, эту строку. Действие получает ключи так же, как массовое действие, поэтому должно проверять
каждую запись.

`batch_edit()` хранит правки в таблице, пока пользователь не сохранит их все. Enter оставляет
изменённую строку в режиме правки с отметкой в начале, а панель над таблицей считает изменённые
строки и показывает «Сохранить изменения» и «Отменить изменения». При сохранении строки уходят по
одной через путь правки в таблице, поэтому каждая читается, проверяется и сверяется по версии
отдельно; строки с ошибкой сохраняют изменения и показывают причину. Загрузка других строк
(страницы, сортировка, фильтры, поиск) спрашивает, прежде чем отбросить несохранённые изменения.

## Главная и подчинённая строки (Master detail)

`detail(|row| (screen, params))` позволяет раскрывать каждую строку в экран, построенный по этой
строке и загружаемый только тогда, когда пользователь его открывает:

```rust
DataGrid::of(search_today)
    .column(Order::id)
    .detail(|o| (order_lines, OrderParams { id: o.id }))

#[screen(permission = "sales.order.read")]
pub fn order_lines(params: OrderParams) -> Screen {
    Screen::window(t!("sales.order_lines", id = params.id.0.to_string())).body(
        DataGrid::of(search_lines)
            .scope(OrderLine::order_id, params.id)
            .column(OrderLine::product)
            .column(OrderLine::amount).sum()
            .detail(|l| (product_editor, ProductParams { id: Some(l.product_id) })),
    )
}
```

Параметры типизированы экраном (`ScreenDef::Params`), поэтому неверные параметры не компилируются.
Detail это полноценный экран: форма, вложенная таблица или таблица со своими detail, на любую
глубину. Столбец с кнопкой раскрытия показывается только пользователям, которым разрешено открывать
экран, а сервер повторно проверяет право на экран при загрузке detail. Параметры проходят через
браузер так же, как у окна, поэтому экран detail должен проверять, что пользователю разрешено видеть
запись, на которую они указывают.

`scope(field, value)` ограничивает таблицу строками, у которых `field` равно `value`, при каждом
запросе. Этот фильтр стоит первым в `DataQuery::filters`, и клиент не может его убрать, так что
вложенная таблица остаётся в пределах своей родительской строки, что бы ни прислал браузер. Слой
данных, строящий SQL из фильтров, читает его как любой другой (`Filter::range` с равными границами
для чисел и дат, `equals` для текста, `any_of` для выбора, `is` для да/нет, `blank` для пустых
значений).

Кнопка раскрытия, Enter на ней или Right и Left на строке открывают и закрывают detail. Закрытие
удаляет его, поэтому в следующий раз он загружается заново.

Виртуальные таблицы держат каждую строку одной фиксированной высоты, чтобы к любой позиции можно было
перейти сразу; кнопки раскрытия они не показывают. Для таблиц с detail используйте страницы или
бесконечную подгрузку.

## Группировка

`group_by(field)` группирует строки на сервере; вызовите его снова, чтобы группировать внутри каждой
группы:

```rust
DataGrid::of(search_today)
    .paging(Paging::pages(20))
    .group_by(Order::city)
    .group_by(Order::status)
    .column(Order::amount).sum().avg()
```

Таблица показывает строку заголовка для каждой группы с названием столбца, значением, числом строк и
итогами всех столбцов по этой группе под соответствующим столбцом. Открытие группы (её кнопкой или
Right и Left) загружает её подгруппы или строки по одной странице, со строкой «Загрузить ещё», если
остались ещё строки; закрытие удаляет их. Верхний уровень разбивается на страницы по группам, поэтому
пейджер считает группы. Нижняя строка хранит итоги по всем подходящим строкам. Строки внутри групп
сохраняют всё остальное: редактирование, действия строк, меню, выбор и detail.

Слой данных отвечает на `DataQuery::group`: когда он задан, возвращается `Page::groups` (значение,
число и итоги, которые запрашивает запрос, для каждой группы), отсортированные по значению в
направлении ключа сортировки по этому полю и разбитые на страницы как строки, где `total` считает
группы. `DataQuery::apply` делает это для данных в памяти; SQL использует `GROUP BY`. `group`
устанавливается таблицей и никогда не читается от клиента. Клиент отправляет только путь значений
групп, которые он открывает; сервер проверяет его длину и превращает каждое значение в фильтр по
столбцу этой группы, перед фильтрами пользователя (`blank` для пустой группы).

## Группировка пользователем и свои итоги

```rust
DataGrid::of(search_orders)
    .column(Order::city).groupable()
    .column(Order::status).groupable()
    .column(Order::profit).sum()
    .column(Order::revenue).sum()
        .summary(t!("orders.margin"), |t| {
            let profit = t.get(Order::profit, Aggregate::Sum)?;
            let revenue = t.get(Order::revenue, Aggregate::Sum)?;
            margin(profit, revenue)
        })
```

`groupable()` позволяет пользователю группировать строки по столбцу: пунктом «Группировать по
этому столбцу» в меню столбца или перетаскиванием заголовка на панель групп над таблицей. Панель
показывает кнопку для каждого уровня, которая его убирает; уровней не больше трёх
(`MAX_USER_GROUPS`). Группы хранятся в представлении пользователя (`DataGridView::group_by`),
сохраняются вместе с ним и, пока заданы, заменяют собственный `group_by` таблицы. Сервер принимает
только группируемые столбцы, никогда маскированные, и группирует так же, как при `group_by`,
поэтому действие отвечает на `DataQuery::group` тем же способом. Деревья и виртуальные таблицы не
группируются.

`summary(label, |t| ...)` добавляет своё значение под столбцом, в подвале и в каждой строке группы.
Оно считается на сервере по `Totals`, то есть по итогам, которые объявляет таблица
(`t.get(field, Aggregate::Sum)`), поэтому строки ему не нужны: маржа из двух сумм, среднее из суммы
и количества. `None` оставляет ячейку пустой. Целые числа разделяются на разряды, деньги и дроби
форматируются на языке пользователя.

## Древовидные данные

`tree(Model::parent)` показывает строки в виде дерева по необязательному ключу родителя: строки без
родителя наверху, а дочерние строки загружаются при открытии строки, по странице за раз, не более
чем на 32 уровня.

```rust
DataGrid::of(search_employees)
    .tree(Employee::manager_id)
    .column(Employee::name)
    .column(Employee::salary).sum()
```

Первый столбец несёт отступ и кнопку. Чтобы узнать, у каких строк есть дочерние, таблица на каждую
страницу делает ещё один запрос к своему action: строки, родитель которых входит в ключи страницы,
сгруппированные по полю родителя (`Filter::any_of` по ключам и `DataQuery::group`). Фильтры и
сортировка применяются на каждом уровне; итоги внизу охватывают все подходящие строки. Древовидные
таблицы не группируют и не показывают detail строк. После редактирования на месте строка остаётся на
своём месте в дереве.

Виртуальные таблицы не группируют и не показывают деревья, так как у каждой строки там одна
фиксированная высота.

## Ячейки: навигация, копирование и вставка

Right на строке (или щелчок по ячейке) ставит в неё курсор ячейки, как в электронной таблице.
Стрелки перемещают его, Shift со стрелкой (или Shift+щелчок) расширяет диапазон, Home и End ведут к
краям строки, а Ctrl+Home и Ctrl+End к первой и последней ячейке таблицы. Tab и Shift+Tab движутся
вдоль строки и дальше к следующей, а на краях покидают таблицу. Left на первой ячейке возвращает к
строке. Enter или F2 редактирует редактируемую ячейку, Enter нажимает единственную кнопку или ссылку
ячейки, Escape снимает диапазон. Ячейки в диапазоне получают `aria-selected`.

Ctrl+C на ячейке копирует диапазон как текст с разделителями табуляции, со значениями в том виде, в
каком их видит пользователь. Ctrl+C на строке по-прежнему копирует выбранные строки.

Ctrl+V на ячейке вставляет текст с разделителями табуляции из электронной таблицы, начиная с
курсора; одно значение заполняет весь диапазон. Меняются только редактируемые ячейки (вставка в
ячейки только для чтения сообщает об этом), варианты выбора можно вставлять по подписи, да и нет на
языке пользователя. Каждая изменённая строка сохраняется через путь редактирования на месте
(`/_zeyn/grid/edit` с версией строки), одна за другой, поэтому каждая строка читается, проверяется и
контролируется на сервере как при редактировании на месте; строка с ошибкой показывает свои ошибки в
своих ячейках, а остальные сохраняются. Для более чем 10 строк запрашивается подтверждение, более
500 отклоняются, а Ctrl+Z отменяет всю вставку. Правки таблицы, действия строк, массовые действия и
действия меню учитываются в `App::write_limit`, поэтому большая вставка может упереться в лимит
записи приложения.

## Виртуализация столбцов

Таблица с 40 столбцами и более держит в странице только закреплённые столбцы и столбцы в области
видимости (плюс до шести с каждой стороны). Каждый столбец получает фиксированную ширину, а одна
ячейка-распорка заменяет пропущенные столбцы с каждой стороны, так что ширины, закрепления и
прокрутка остаются прежними. Строки сохраняют полный список ячеек, поэтому копирование, вставка и
редактирование видят каждый столбец, а ячейки несут `aria-colindex`. Окно сдвигается только тогда,
когда в область видимости попадает столбец вне его. Сервер по-прежнему отправляет каждую ячейку
строки. Такая широкая виртуальная таблица (`VIRTUAL_WIDE_COLUMNS`, считая столбцы выбора, детализации
и действий строки) отправляет весь первый блок внутри `<template data-zeyn-rows-later>` вместо 64 живых
строк, так что браузер никогда не раскладывает строку со всеми столбцами: на широкой таблице галереи
самая долгая задача запуска сократилась с 259 до 112 мс, а DOMContentLoaded с 402 до 228 мс (медианы
8 чередующихся загрузок, release-сервер, загруженная машина).

Измерено на широкой таблице галереи (62 столбца, 100 000 строк, виртуальная прокрутка, debug-сервер,
Chromium, окно 1400 на 900, дисплей 144 Гц), с виртуализацией столбцов и без неё:

| | Ячеек в странице | В сторону, 60 px за кадр (p50 / p95) | Вниз, 60 px за кадр (p50 / p95) | Вниз, 2000 px за кадр (p50 / p95) |
|---|---|---|---|---|
| Без | 2 976 | 6,9 / 7,5 мс | 42,7 / 64,8 мс | 78,5 / 141 мс, 178 долгих задач |
| С | 1 056 | 7,0 / 28,8 мс | 24,6 / 41,7 мс | 28,9 / 48,9 мс, 7 долгих задач |

Прокрутка вниз примерно вдвое быстрее, а страница держит треть ячеек. Прокрутка в сторону и так была
плавной; кадры, в которых окно сдвигается, стоят до 29 мс. Остальная стоимость приходится на разбор
блоков по 200 строк со всеми столбцами, чего виртуализация столбцов не меняет.

## Экспорт

`exportable()` (и, по желанию, `export_permission(...)`, `export_limit(n)`) позволяет кнопке
`Export::Csv` на панели инструментов скачать все подходящие строки. Сервер постранично обходит action
таблицы и сразу передаёт каждую страницу потоком, в раскладке и на языке пользователя. Формулы
обезвреживаются. По умолчанию до 100 000 строк. Пока строки выбраны (по одной, а не «все подходящие»), экспорт в CSV и Excel берёт только их, не больше 1 000, по-прежнему в пределах фильтров пользователя; сервер находит их по ключу.

С Cargo-feature `xlsx` кнопка `Export::Xlsx` на панели инструментов скачивает те же строки как книгу
Excel (`GET /_zeyn/grid/export?format=xlsx`). Ячейки сохраняют свои типы: числа, деньги как число с
денежным форматом, даты и даты со временем как настоящие даты Excel в часовом поясе пользователя и
логические значения. Варианты выбора записываются как их подписи, маскированные поля как их
маскированный текст, а текст всегда остаётся текстом, поэтому ничто не становится формулой. Строка
заголовков содержит подписи на языке пользователя, выделена жирным и закреплена, а столбцы
сохраняют порядок и ширину пользователя.

Книга записывается с `rust_xlsxwriter` в режиме постоянной памяти: каждая страница по мере прихода
уходит во временный файл (в памяти ждут не более двух страниц), а сжатая книга в конце передаётся
потоком в ответ. Экспорт 100 000 строк из шести столбцов держал кучу около 134 KiB при записи строк
(столько же после 10 000 и после 100 000 строк) и 460 KiB при сжатии; файл занял 3,4 МБ.

С Cargo-feature `pdf` кнопка `Export::Pdf` печатает те же строки как отчёт-список (не более 2000
строк); см. [PDF documents](operations.md#pdf-documents).

## Выбор

`selectable()` (подразумевается в `bulk_action`) добавляет столбец с флажками. Shift выбирает
диапазон, Space выбирает строку в фокусе, а флажок в заголовке выбирает страницу. Панель выбора
предлагает все подходящие строки.

## Доступность

У таблицы есть `role="grid"`, `aria-rowcount` (виртуальные таблицы), `aria-colcount`,
`aria-colindex` и `aria-sort`. Строки используют перемещаемую точку табуляции (roving tab stop).
Кнопки внутри активной строки достижимы клавишей Tab. Сгруппированные и древовидные таблицы имеют
`role="treegrid"` с `aria-level` и `aria-expanded` на строках. Меню используют `role="menu"` с
`menuitem`, `menuitemcheckbox` и `menuitemradio`, а фокус возвращается туда, где он был. Пустое
состояние и состояния ошибки озвучиваются (`role="status"`).

Измерено на архиве showcase (1 000 000 строк, виртуальная прокрутка, debug-сервер, Chromium, дисплей
144 Гц) с помощью Performance API:

| Скорость колеса (60 px за кадр) | 13,9 мс | 20,9 мс | 34,6 мс | 0 |
| Быстрая (2000 px за кадр) | 14,1 мс | 27,8 мс | 54,9 мс | 0 |

### Держите построитель экрана дешёвым

Запросы не хранят состояния, поэтому каждый запрос таблицы заново строит экран, в котором она лежит: каждый блок, который загружает виртуальная таблица (каждые 200 прокрученных строк), каждая страница, сортировка, фильтр и экспорт, каждое встроенное редактирование и каждое действие строки снова запускают функцию `#[screen]` перед действием таблицы. Серверу нужен экран, чтобы найти таблицу по пути узла и проверить доступ, так что это цена отказа от состояния на пользователя.

Построитель, который только раскладывает компоненты, стоит микросекунды. Построитель, который обращается к базе данных, платит за этот запрос при каждом из таких запросов. Поэтому:

- Загружайте строки в действии таблицы (`DataGrid::of(search)`). Оно всё равно выполняется один раз за запрос и получает `DataQuery` со страницей, сортировкой и фильтрами.
- Варианты выбора и справочники относятся к типу поля (`#[choice]`), к поиску формы (`Form::lookup`, который обращается к своему действию, когда пользователь печатает) или к сервису, который держит их в кэше с ограничением, а не к запросу, который выполняет построитель.
- Когда экран должен загрузить запись (`Form::of(record)`), не кладите на него большие или виртуальные таблицы: вынесите их на отдельный экран, в экран детализации (`DataGrid::detail`) или в окно, чтобы их запросы блоков перестраивали экран, который ничего не загружает.
- Параметры экрана это входные данные построителя; ограничьте их ключами и пусть действие таблицы фильтрует по ним (`DataGrid::scope`).
